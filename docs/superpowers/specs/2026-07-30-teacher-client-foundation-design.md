# SchoolWorkHub 교사용 클라이언트 기반 설계

- 작성일: 2026-07-30
- 대상 저장소: `KANG77556/HUB`
- 대상 브랜치: `feat/bootstrap-foundation`
- 상태: 사용자 승인 완료 설계

## 1. 목적

Electron 기반 교사용 클라이언트의 첫 번째 실제 동작 범위를 정의한다. 이 범위는 로그인, 자동 세션 복구, 복수 역할 권한 통합 대시보드, 오프라인 읽기 전용 모드, 서버 신원 검증, 보호된 서버 설정 변경과 자동 테스트까지 포함한다.

이 설계의 핵심 목표는 다음과 같다.

1. 교사가 앱을 실행하면 별도 조작 없이 안전하게 세션을 복구한다.
2. 역할별로 다른 앱을 만들지 않고, 하나의 공통 대시보드에서 권한에 맞는 메뉴와 카드만 노출한다.
3. 네트워크 장애 중에도 최근 업무 현황을 읽기 전용으로 확인할 수 있게 한다.
4. 토큰, 캐시, 서버 주소와 TLS 인증서 검증을 Electron 메인 프로세스 안에 격리한다.
5. 인증서 불일치, 토큰 거부, 네트워크 장애를 서로 다른 상태로 처리한다.

## 2. 범위

### 포함

- 학교 코드, 사용자명, 비밀번호 기반 최초 로그인
- 15분 액세스 토큰과 30일 갱신 토큰
- 갱신 토큰의 Windows 자격 증명 관리자 저장
- 앱 실행 시 자동 세션 복구
- 동시 401 발생 시 단일 토큰 갱신
- 사용자 역할과 권한 합집합 계산
- 권한 기반 공통 대시보드와 메뉴 노출
- 최근 30일 대시보드·일정·문서 목록의 암호화 오프라인 캐시
- 오프라인 고정 배너와 읽기 전용 잠금
- 재연결 후 백그라운드 증분 동기화와 변경 요약
- 현재 인증서와 다음 인증서의 지문 동시 신뢰
- 관리자 인증이 필요한 서버 주소 변경
- 메인, 프리로드, 렌더러, 통합, Windows CI 테스트

### 제외

- 오프라인 생성·수정·제출과 충돌 해결
- 문서 본문 및 첨부파일 오프라인 저장
- 문서 편집기, 일정 상세 편집, 업무 제출 화면
- 다중 학교를 동시에 사용하는 계정 전환
- macOS와 Linux용 보안 저장소 구현
- 별도 백그라운드 Windows 서비스

## 3. 접근 방식

보안 중심 Electron 계층 분리를 사용한다.

- Electron 메인 프로세스가 인증, API 호출, 자격 증명 관리자, DPAPI, SQLite, TLS 검증을 담당한다.
- 프리로드는 허용된 명령만 `contextBridge`로 노출한다.
- React 렌더러는 토큰, 서버 주소 원본, 인증서 지문 원본에 직접 접근하지 않는다.
- 로컬 캐시는 사용자별로 암호화하며, 업무 데이터는 최근 30일의 요약 정보만 보관한다.

렌더러 중심 구현은 토큰과 TLS 경계가 약해지므로 사용하지 않는다. 별도 로컬 서비스 구조는 현재 범위에 비해 설치와 운영 복잡도가 크므로 사용하지 않는다.

## 4. 전체 아키텍처

### 4.1 Electron 메인 프로세스

책임:

- BrowserWindow 수명주기와 보안 옵션 관리
- 학교 서버 주소와 신뢰할 인증서 지문 로드
- HTTPS 요청과 인증서 체인·지문 검증
- 로그인, 토큰 갱신, 로그아웃
- 액세스 토큰의 메모리 보관
- 갱신 토큰의 Windows 자격 증명 관리자 보관
- 사용자별 DPAPI 키 보호와 SQLite 캐시 접근
- 네트워크·인증·설정·보안 오류 분류
- IPC 요청 검증과 응답 직렬화

BrowserWindow 기본 보안 옵션:

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- `enableRemoteModule: false`
- 외부 탐색과 새 창은 명시적 허용 목록으로 제한

### 4.2 프리로드 계층

프리로드는 아래 명령만 노출한다.

- `auth.login`
- `auth.restoreSession`
- `auth.logout`
- `dashboard.load`
- `connection.getStatus`
- `settings.requestServerChange`
- `events.onConnectionChanged`
- `events.onSyncSummary`
- `events.onSessionInvalidated`

프리로드는 임의 채널 이름, 원시 IPC 객체, 토큰, 인증서, 파일 시스템 경로를 렌더러에 노출하지 않는다. 모든 입력과 출력은 고정된 타입과 스키마로 검증한다.

### 4.3 React 렌더러

책임:

- 로그인 화면
- 자동 로그인 진행 상태
- 공통 대시보드
- 역할 배지와 권한 기반 메뉴
- 온라인·오프라인·재연결·보안 차단 상태 표시
- 오프라인 읽기 전용 잠금
- 동기화 변경 요약
- 보호된 서버 설정 변경 진입 화면

렌더러는 토큰을 보관하거나 직접 HTTP 요청을 만들지 않는다.

### 4.4 로컬 데이터 계층

SQLite를 사용하되, 민감 데이터 열과 페이로드는 Windows 사용자별 DPAPI로 보호한다.

캐시 식별자는 다음 조합을 사용한다.

- Windows 사용자 보안 식별자
- SchoolWorkHub 사용자 ID
- 학교 ID

다른 Windows 계정 또는 다른 SchoolWorkHub 사용자는 기존 캐시를 복호화하거나 조회할 수 없어야 한다.

## 5. 인증과 세션

### 5.1 토큰 정책

- 액세스 토큰 수명: 15분
- 갱신 토큰 수명: 30일
- 액세스 토큰 저장 위치: Electron 메인 프로세스 메모리
- 갱신 토큰 저장 위치: Windows 자격 증명 관리자
- 렌더러 전달: 금지

### 5.2 최초 로그인

1. 사용자가 학교 코드, 사용자명, 비밀번호를 입력한다.
2. 렌더러가 `auth.login`을 호출한다.
3. 메인 프로세스가 학교 서버와 TLS 신원을 검증한다.
4. `/api/v1/auth/login`을 호출한다.
5. 성공 시 갱신 토큰은 자격 증명 관리자에 저장하고 액세스 토큰은 메모리에 보관한다.
6. `/api/v1/auth/me`를 호출해 사용자, 역할, 권한을 가져온다.
7. 대시보드 데이터를 로드하고 암호화 캐시를 갱신한다.

### 5.3 앱 시작 자동 로그인

1. 서버 설정과 인증서 지문 정책을 읽는다.
2. 자격 증명 관리자에서 갱신 토큰을 조회한다.
3. 토큰이 없으면 로그인 화면을 표시한다.
4. 토큰이 있으면 `/api/v1/auth/refresh`를 호출한다.
5. 새 액세스 토큰으로 `/api/v1/auth/me`를 호출한다.
6. 성공 시 온라인 대시보드를 표시한다.
7. 네트워크 장애면 캐시를 읽기 전용으로 표시한다.
8. 갱신 토큰 거부면 토큰과 캐시를 삭제하고 로그인 화면을 표시한다.
9. 인증서 불일치면 보안 차단 화면을 표시한다.

### 5.4 단일 갱신 잠금

여러 요청이 동시에 401을 받아도 갱신 요청은 하나만 수행한다.

- 첫 요청이 갱신 Promise를 생성한다.
- 후속 요청은 같은 Promise를 기다린다.
- 성공하면 대기 요청을 새 액세스 토큰으로 한 번 재시도한다.
- 실패하면 세션을 폐기하고 `sessionInvalidated` 이벤트를 전송한다.
- 무한 재시도는 허용하지 않는다.

### 5.5 로그아웃과 강제 세션 폐기

다음 상황에서는 갱신 토큰과 해당 사용자의 오프라인 캐시를 즉시 삭제한다.

- 사용자가 로그아웃
- 갱신 토큰 거부 또는 폐기
- 계정 비활성화
- 학교 소속 해제

단순 네트워크 장애와 서버 점검에서는 캐시를 유지한다.

## 6. 역할과 권한

사용자가 여러 역할을 가진 경우 역할별 대시보드를 나누지 않는다. 모든 역할의 권한을 합집합으로 계산하고 하나의 공통 대시보드에 적용한다.

예시 권한 코드:

- `documents.read`
- `submissions.read`
- `calendar.read`
- `users.manage`

원칙:

- 역할 이름은 화면 배지에 사용한다.
- 메뉴, 카드, 행동 버튼은 권한 코드로 결정한다.
- 권한 없는 메뉴는 비활성화하지 않고 숨긴다.
- 클라이언트 표시 제어와 무관하게 서버 API가 권한을 다시 검증한다.
- 사용자 권한이 동기화 중 변경되면 화면을 증분 갱신한다.

## 7. 대시보드

공통 구조:

- 상단 통합 검색
- 알림 진입점
- 역할 및 부서 배지
- 오늘의 일정 카드
- 제출 대기 카드
- 새 문서 카드
- 오늘의 업무 흐름
- 권한에 따라 노출되는 좌측 메뉴

최초 범위에서 대시보드 데이터는 요약 정보만 포함한다. 상세 편집 기능은 다음 하위 프로젝트로 분리한다.

## 8. 오프라인 캐시

### 8.1 보관 범위

최근 30일의 다음 데이터만 저장한다.

- 대시보드 요약
- 일정 목록과 요약 상태
- 문서 목록과 요약 상태
- 제출 대기 수와 상태 요약
- 역할과 권한 스냅샷
- 마지막 성공 동기화 시각

저장하지 않는 데이터:

- 비밀번호
- 액세스 토큰
- 갱신 토큰
- 문서 본문
- 첨부파일
- 상담 상세 내용
- 서버 인증서 개인 키

### 8.2 암호화

- SQLite 파일 자체는 사용자별 저장 경로에 둔다.
- 캐시 페이로드를 데이터 키로 암호화한다.
- 데이터 키는 DPAPI 사용자 범위로 보호한다.
- 복호화 실패, Windows 사용자 불일치, 사용자 ID 불일치 시 캐시를 폐기한다.

### 8.3 만료와 정리

- 30일보다 오래된 레코드는 온라인 동기화 후 정리한다.
- 앱 시작 시에도 만료 정리를 수행한다.
- 로그아웃과 강제 세션 폐기 시 해당 사용자의 캐시를 완전히 삭제한다.

## 9. 연결 상태와 재동기화

연결 상태는 다음 네 가지다.

- `online`
- `offline-readonly`
- `reconnecting`
- `security-blocked`

### 온라인

서버 데이터를 사용하고 성공 응답을 캐시에 반영한다.

### 오프라인 읽기 전용

- 화면 상단 고정 배너 표시
- 마지막 동기화 시각 표시
- 생성·수정·제출 버튼 비활성화
- 캐시된 대시보드·일정·문서 목록 조회 허용

### 재연결 중

현재 화면과 스크롤 위치를 유지한다. 백그라운드에서 증분 데이터를 가져오며 전체 페이지 새로고침은 하지 않는다.

동기화 대상:

- 새 일정과 변경된 일정
- 새 문서와 상태 변경 문서
- 제출 대기 수와 처리 상태
- 역할과 권한 변경

완료 후 예시처럼 요약한다.

- 새 일정 2건
- 새 문서 3건
- 제출 상태 변경 1건

### 보안 차단

TLS 인증서 지문 불일치 또는 서버 식별 실패 시 업무 화면과 캐시 화면 모두 차단한다. 사용자가 단순 재시도로 우회할 수 없으며 관리자 조치 흐름만 제공한다.

## 10. 서버 주소와 TLS 인증서 고정

### 10.1 기본 배포

학교 서버 주소와 인증서 지문은 설치 시 관리자가 배포한다. 교사는 정상 상황에서 서버 주소를 입력하지 않는다.

### 10.2 인증서 검증

연결 전 다음을 모두 검증한다.

1. HTTPS 사용
2. 인증서 체인 유효성
3. 호스트 이름 일치
4. 현재 또는 다음 인증서 지문 일치
5. SchoolWorkHub 서버 식별 응답
6. API 버전 호환성

현재 인증서와 다음 인증서의 지문을 일정 기간 함께 신뢰한다. 새 인증서 배포가 완료된 뒤 기존 지문을 제거한다.

### 10.3 보호된 서버 변경

서버 주소 변경은 연결 실패 화면에서만 진입할 수 있으며 관리자 암호 또는 관리자 권한 계정 인증이 필요하다.

변경 절차:

1. 관리자 인증
2. 새 서버 주소 입력
3. 현재·다음 인증서 지문 입력 또는 정책 파일 적용
4. 시험 연결
5. 서버 식별과 API 버전 검증
6. 관리자 권한 확인
7. 모든 검증 성공 시 원자적 저장

시험 연결이 하나라도 실패하면 기존 설정을 유지한다. 설정 파일은 임시 파일에 기록한 뒤 원자적으로 교체한다.

## 11. 오류 모델

### 재시도 가능

- 일시적 네트워크 장애
- 서버 점검
- DNS 해석 실패
- 연결 시간 초과

행동: 캐시가 있으면 오프라인 읽기 전용, 없으면 재시도 화면.

### 로그인 필요

- 갱신 토큰 만료 또는 폐기
- 계정 비활성화
- 소속 변경으로 세션 무효화

행동: 토큰과 캐시 삭제 후 로그인 화면.

### 관리자 조치 필요

- 서버 주소 오류
- API 버전 불일치
- 학교 코드와 서버 불일치

행동: 보호된 서버 설정 변경 진입 제공.

### 보안 차단

- 인증서 지문 불일치
- 인증서 체인 또는 호스트 이름 검증 실패
- SchoolWorkHub 서버 식별 실패

행동: 모든 업무·캐시 화면 차단, 감사 로그 가능한 보안 오류 코드 기록.

## 12. 데이터 및 IPC 계약

렌더러에 전달하는 세션 정보는 다음 수준으로 제한한다.

```ts
interface SessionView {
  userId: string;
  displayName: string;
  schoolName: string;
  departmentNames: string[];
  roles: string[];
  permissions: string[];
}
```

연결 상태:

```ts
type ConnectionState =
  | { kind: 'online'; lastSyncAt: string }
  | { kind: 'offline-readonly'; lastSyncAt: string | null }
  | { kind: 'reconnecting'; lastSyncAt: string | null }
  | { kind: 'security-blocked'; code: string };
```

로그인, 세션 복구, 대시보드 응답에는 토큰과 원시 서버 오류 내용을 포함하지 않는다. 사용자 메시지와 내부 진단 코드는 분리한다.

## 14. 완료 기준

다음 조건을 모두 만족해야 이 하위 프로젝트가 완료된다.

1. 로그인, 자동 토큰 갱신, 자동 로그인, 로그아웃이 실제 API와 연동된다.
2. 갱신 토큰은 Windows 자격 증명 관리자에만 저장된다.
3. 액세스 토큰은 렌더러와 디스크에 노출되지 않는다.
4. 복수 역할 권한 합집합이 공통 대시보드에 반영된다.
5. 최근 30일 캐시가 사용자별 DPAPI 보호를 받는다.
6. 오프라인에서는 읽기 전용 화면과 고정 배너가 표시된다.
7. 재연결 후 전체 새로고침 없이 증분 동기화와 변경 요약이 동작한다.
8. 현재·다음 인증서 지문을 모두 지원한다.
9. 인증서 불일치 시 업무와 캐시 접근이 차단된다.
10. 서버 변경은 관리자 인증과 시험 연결 성공 후에만 저장된다.
11. 로그아웃과 강제 세션 폐기 후 토큰과 사용자 캐시가 삭제된다.
12. 정의된 자동 테스트와 Windows CI가 모두 통과한다.
